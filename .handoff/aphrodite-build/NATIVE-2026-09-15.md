# Aphrodite 0.2: preserve the designer

Work item: `mn-6c5d94`. User direction, 2026-09-15: improve normal AI frontend design rather than replace the abilities it already has; generalize through relationships and perspectives.

## What went wrong

The 0.1 `compose` path accepts a hand-authored semantic brief, expands a small layout grammar, varies five shared controls, emits HTML/CSS, observes it, and selects using nine authored feature families. There is no AI designer inside that loop. Its high values measure agreement with those chosen targets. Functional eligibility does not establish beauty. Its fitter can change nine feature weights, but cannot acquire a missing composition technique; `neither` records are excluded from pairwise fitting.

Erik rejected the generated set. The linked Claude artifact could not be opened in this session; the architecture diagnosis comes from the current source and Erik's supplied report, not an independent visual inspection of that artifact. Rejection establishes a failed outcome. By itself it does not identify the exact contribution of vocabulary, search, descriptors, and objective.

The primary correction is to preserve the host AI's native design ability. A numerical instrument should help the designer express and maintain relationships. It should not force the designer to reconstruct a project through the smaller legacy vocabulary.

## What is implemented

`agent-do aphrodite packet` now defaults to a native design packet. It accepts an ordinary brief or the current conversation/project, and packages a design workflow, conditional relationship vocabulary, an empty authored graph, and portable runtime. The default packet includes neither the legacy renderer nor its scoring model. Registry discovery and the generated tool catalog recommend this route. Explicit `--mode engine` preserves the previous packet and replay path.

The workflow starts with the intended encounter, subject matter, visual character, and the host's normal frontend process. It asks the designer to preserve strong existing work, make consequential relationships explicit, implement them in native code, render, and choose revisions using its ordinary visual judgment. That judgment is attributed to the host and is not recorded as human approval or empirical validation.

An open graph accepts arbitrary named inputs, derived mathematical expressions, and CSS-variable bindings. It carries explanations for the selected relationships. It has no prescribed layout, fonts, colors, five-control limit, or taste weights. `describe --relations` resolves it; `revise --relations` emits a successor graph, CSS, and a dependency receipt. A browser-compatible `applyRelations` applies only those custom properties to an existing element after full validation. Plain CSS can remain the better implementation for a relationship that it already expresses clearly.

Nonnumerical relations such as material associations, image meaning, typeface selection, and responsive topology remain with the AI's code and design notes. Numerical units must be chosen consistently by the author. The runtime does not claim to automate those judgments.
